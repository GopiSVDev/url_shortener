# Load test results

Highest rate each test sustained for the full confirm run within its target.
Generated by `node loadtest/find-capacity.mjs <test> [note]`.
CPU columns are average cores used during the confirm run (limit in brackets).
Backend limited to 0.6 CPU, Postgres to 0.4 CPU.

Capacity is given as a range: near the limit the same build passes or fails depending on the run. The 0.6 CPU
limit is enforced per 100 ms, so a short burst (GC, cache misses) freezes the backend for the rest of the window,
a queue forms, and at ~95% load there is little spare CPU to drain it. The low end is the lowest confirmed
(2-minute) result of the final build, the high end the best confirmed or short-hold pass within the same target.

## write: `POST /api/urls` (anonymous create)

### Summary

**890 -> 1185-1415 req/s (+33% to +59%)**, CPU per request 0.51 -> 0.34 ms (-34%), p99 217 -> 21 ms.

- Built a capacity test (k6 + Prometheus) that finds the highest rate held for 2 minutes within p90/p95/p99 targets.
- Profiled with async-profiler: Spring Security observations cost ~10% of CPU; disabled them (+9%).
- Measured SQL per request from `pg_stat_statements`; replaced the JPA save with one JDBC insert in autocommit (2 -> 1 statement, ~+15% over the previous change).
- Found that overload collapses with 200 Tomcat threads on 0.6 CPU and 10 DB connections; capped threads at 50 so queues drain (+6%).
- With the latency limits doubled (p99 <= 1000 ms) the same build holds 1415 req/s at p99 209 ms, which also met the
  strict target on its 2-minute hold (the high end of the range); raw maximum ~1600 req/s at 0.6 CPU.
  The strict target is limited by short CPU bursts (the 0.6 CPU limit is enforced per 100 ms), not by average CPU.

## read: `GET /{code}` (redirect, 1M links, Zipf traffic)

### Summary

**1295 -> 2625-3160 req/s (+103% to +144%)**, CPU per request 0.36 -> ~0.2 ms (-45%), DB CPU 0.238 -> ~0.12 cores.

- Seeded a fixed dataset of 1M links and replayed Zipf-distributed traffic (97% live, 2% unknown, 1% expired links).
- Replaced the JPA lookup in a read-only transaction with one JDBC select in autocommit, fetching only the two
  columns a redirect needs (2 -> 1 statement, +41%).
- Profiled with async-profiler and took public redirects out of the Spring Security filter chain (+9%), and ran
  the JWT filter only inside the security chain with open-in-view off (-3% CPU per request in the profile).
- Added an in-process Caffeine cache (100k entries, 404s cached, expiry checked per hit, evicted after commit on
  update/delete): SQL per request 1.0 -> 0.24, DB CPU -59%, CPU per request -12%, capacity +32% (2625; a repeat
  run held 2770). The capacity gain is larger than the CPU saving because most requests no longer compete for the
  10 DB connections at the limit.
- Chose Caffeine over Redis because backend CPU is the bottleneck and a Redis lookup would still cost a network round trip.
- With the latency limits doubled (p99 <= 1000 ms) the same build holds 3160 req/s at p90 164 ms / p99 334 ms
  (p95 215 ms misses the strict target), though a 1-minute step at 3160 met it (the high end of the range);
  raw maximum ~3150 req/s at 0.6 CPU. Past ~2900 req/s the backend runs saturated and requests queue: p90 goes
  from 0.5 ms to 100+ ms for the last 10% of throughput.
- Now hardware bound: the backend sits at its 0.6 CPU limit, and ~75% of its CPU is HTTP handling (Tomcat, Spring MVC,
  socket I/O) that every request pays.
